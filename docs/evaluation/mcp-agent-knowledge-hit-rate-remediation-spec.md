# MCP Agent 知识命中准确率修复 SPEC

> 依据：`docs/evaluation/mcp-agent-knowledge-hit-rate-test-report.md`（2026-07-27）。
>
> 目标：修复 MCP `search` / `ask` 在真实 Agent 调用场景下的召回、拒答、版本识别与条款事实错误问题；修复后必须以同一 Golden Set 复测，而非只通过单元测试。

## 1. 背景与问题定义

本轮 37 条 Golden Set 测试中，可回答用例 32 条。当前关键指标为：

| 指标 | 当前值 | 最低通过线 | 推荐目标 |
| --- | ---: | ---: | ---: |
| Top-1 Accuracy | 59.38% (19/32) | 75% | 85% |
| Recall@5 | 65.62% (21/32) | 88% | 95% |
| Answer Groundedness | 40.62% (13/32) | 90% | 96% |
| Citation Validity | 70.48% (148/210) | 95% | 98% |
| Hallucination Rate | 3.12% (1/32) | <= 5% | <= 2% |
| False Positive Rate | 0.00% (0/5) | <= 10% | <= 5% |

根因已被报告和现有代码共同确认：

1. `search` 与 `ask` 对同一证据使用不同评分上下文，`ask` 会拒绝 `search` 已正确接受的证据。
2. `no_match_threshold=0.35` 将口语化查询的所有候选直接过滤为空。
3. 包含“最新”的本地制度版本查询被误判为实时外部信息，未执行检索。
4. 并列条款的相邻证据未一起提供给问答链路，导致 II 类/III 类金额混淆。
5. 新旧版本文档缺乏稳定的版本优先排序；近似重复件会挤占 Top-K。

## 2. 目标、非目标与约束

### 2.1 本次必须达成的目标

- 修复报告列出的 18 个 P1，并保持 5 个无答案用例不发生错误确定性回答。
- 所有“`search` 已接受候选”的用例，`ask` 不得再因同一证据被二次低分误拒答。
- “最新版本 / 最新修订版 / 现行办法”等本地版本问题必须进入本地检索；真正实时问题仍必须拒答。
- 账户限额、资费、处罚、时限等数值问题，回答中的数字必须来自可定位证据，不能以相邻类别数值替代。
- 为问题增加自动化回归测试，并更新测试报告。

### 2.2 非目标

- 不替换 Embedding、Reranker 或 LLM 服务商；除非诊断证明某通道不可用，且先单独提交证据和方案。
- 不修改 Golden Set 的预期知识 ID、必需事实、禁止事实来“提高通过率”。
- 不把所有低分候选无条件送入 LLM，也不以简单降低全局阈值换取召回。
- 不通过删除无答案保护、关闭 evidence gate、扩大 `top_k` 等方式掩盖问题。
- 本轮不引入新的数据库 Schema；若去重需要改数据，先以可回滚的导入/索引逻辑实现。

### 2.3 兼容与安全约束

- 保持 MCP `search`、`ask` 的现有成功/失败 envelope 不变；新增字段必须向后兼容。
- “无足够证据”仍应返回 `answer_mode=no_answer`，且不得附带被当作答案的错误数字。
- 不在日志、报告或测试中输出密钥、完整内部敏感文档内容。
- 所有实现需经单元测试、目标回归测试和 Golden Set 端到端复测。

## 3. 交付物

修复 Agent 必须提交以下内容：

1. 源码和测试变更；
2. 一份变更说明：每一项改动对应的报告用例、根因和风险；
3. 新增/更新的自动化测试；
4. Golden Set 复测的原始 MCP 调用记录和更新后的 Markdown 报告；
5. 若修改了分块或导入逻辑：明确是否已重建测试索引、索引时间、文档数和 block 数；
6. 未解决问题清单（如有），不得省略失败用例。

## 4. 实施顺序

按以下顺序实现与验证。每完成一个阶段都应先运行对应测试，再进行下一阶段；不要把所有改动混成一次无法定位的修改。

### 阶段 0：建立基线与保护测试

1. 不修改 `evals/golden_set_hit_rate.json` 和现有原始 artifacts。
2. 从 `artifacts/hit_rate_test/final_scored.json` 提取失败清单，建立可重复执行的回归集合：

   - `answer_pipeline`：KB-007、009、014、016、017、023、027；
   - `retrieval_recall`：KB-010、011、012、015、018、020、021、028；
   - `routing`：KB-035、037；
   - `hallucination`：KB-019；
   - 无答案保护：KB-030--034。

3. 在现有测试基础上新增一个聚焦回归文件。推荐路径：`tests/mcp/test_hit_rate_regressions.py`；若项目已有更合适的 MCP 测试目录，可放在该目录，但需说明原因。
4. 回归测试需使用稳定的 fake candidates / fake pipeline，不依赖网络 Embedding 或外部 LLM；真实 MCP Golden Set 用于阶段 6 的端到端确认。

### 阶段 1：统一 `search` 与 `ask` 的证据判定（P1-A，最高优先级）

#### 现状

- `search` 在 `src/mcp/tools/retrieval.py` 中对检索候选执行 `evaluate_evidence()`；
- `ask` 先运行问答服务，再对返回的 `sources` 重新执行 `evaluate_evidence()`，失败后将答案和来源清空；
- 因候选对象字段、片段内容或评分上下文不同，产生了“`search`=1.0、`ask`=0.0957”的不一致。

#### 实现要求

1. 建立一个唯一的“可回答证据判定”入口。它必须接收规范化后的候选，并输出：
   - 已接受的候选列表；
   - `top_score`、阈值、拒绝原因；
   - 每个候选的 `knowledge_id` / block 标识 / relevance 详情；
   - 可序列化的 `decision_id` 或等效的可追踪标识（可选，但推荐）。
2. `ask` 在调用 LLM/AnswerService **之前**使用该入口取得接受证据。没有接受证据时，必须短路返回 `no_answer`，不得调用生成链路。
3. `ask` 在生成后只能进行“引用完整性校验”：最终引用的知识 ID / block 必须属于预先接受的证据或其明确扩展上下文；不得再用不同字段对同一证据重新打分并推翻先前接受结果。
4. `search` 和 `ask` 对同一查询、同一候选集合的 `final_relevance_score` 必须一致（允许显示层排序/截断不同，但不得改变判定）。
5. 保留弱证据防幻觉能力：真正没有可接受证据时，仍必须清空回答并返回 `no_answer`。

#### 必须新增的测试

- 已接受的强证据即使 `ask` 的来源对象缺失原始 `score` 字段，也不得被拒答。
- 弱证据场景不调用 LLM/管线，并保持 `no_answer`；现有 `tests/stability/test_pre_llm_evidence_gate.py` 必须继续通过。
- 对应 KB-017 的 synthetic case：正确候选包含“2000元/个”，`search` 和 `ask` 均接受，`ask` 最终包含该事实和来源。
- 对应 KB-007/016/023/027 的 synthetic regression：不再出现“search 命中、ask 空答案”。

### 阶段 2：修复本地版本查询的实时意图误判（P1-C）

#### 现状

`_CURRENT_INFO_RE` 直接将“最新”视为实时信息，导致 KB-035、KB-037 在检索前返回 `requires_current_external_data`。

#### 实现要求

1. 将二元正则判断升级为最小可维护的意图分类：
   - `live_external`：今天/实时/行情/股价/刚刚等需要外部实时数据的问题；
   - `local_version`：最新版本、最新修订版、现行办法、现行制度、最新文号等需要在本地库比较版本的问题；
   - `ordinary`：其余问题。
2. 仅 `live_external` 可在检索前短路为 `requires_current_external_data`。
3. `local_version` 必须进入正常检索，并在阶段 4 的版本排序中优先返回最新有效制度；若库中没有版本信息，应诚实说明“未能从本地资料确定最新版本”，而非伪造实时拒答。
4. 保留已有实时保护：例如“中国电信股价今天多少”“当前实时行情”“火星探测任务最新进展”仍需拒答，不得调用检索/生成管线。

#### 必须新增的测试

- `is_current_information_query` 或其替代分类接口：
  - `中国电信股价今天多少` => `live_external`；
  - `量子计算最新进展` => `live_external`；
  - `差旅费管理办法最新版本是哪一年` => `local_version`；
  - `技能竞赛管理办法最新修订版` => `local_version`。
- `search`、`ask` 对两个 `local_version` case 不得提前返回 `requires_current_external_data`。
- 既有 `tests/stability/test_current_information_no_answer.py` 的实时拒答断言必须保留。

### 阶段 3：改善低词面匹配查询的召回，但不破坏拒答（P1-B）

#### 现状

8 条自然语言查询被 `no_match_threshold=0.35` 过滤为零候选。当前评分还会对任何包含数字单位、但未在候选片段中精确匹配的查询施加硬上限；年份、文号等“检索条件”不应与“用户要求回答的数值”混为一谈。

#### 实现要求

1. 保持 `0.35` 作为高置信“可直接回答”阈值，不得简单下调全局数值。
2. 将“候选展示”和“是否可直接生成回答”分离：
   - 高置信候选：保持当前正常行为；
   - 存在检索候选但未达高置信：允许以向后兼容的方式返回最多 `top_k` 条低置信候选，并明确标注低置信状态、实际分数和拒绝原因；
   - 没有候选：仍返回空列表。
3. 对低词面匹配查询，选择并实现一种可解释的二次召回策略；优先复用项目已有的 Hybrid/FTS/Reranker 能力。可选方案包括查询别名扩展、查询改写、候选 rerank 或词面/语义融合，但必须记录选择理由及其对无答案集的影响。
4. 修正数值匹配惩罚：
   - 年份、文号、版本号等作为过滤条件时，不能因候选正文没有出现同一数字而被硬性压到阈值以下；
   - 对确实询问金额、比例、时限等数值答案的问题，仍要保留“单位不一致”的降权与防混淆能力；
   - 通过函数语义和测试区分上述两类，禁止以移除全部数值校验解决问题。
5. 添加必要的检索 trace/调试字段（仅在现有安全 envelope 或测试 trace 内）：vector、FTS、rerank、relevance 各阶段是否参与及分数。`vector_score=null` 只能作为诊断线索，不能直接得出“向量检索未生效”的结论。

#### 验收用例

修复后以下查询至少要使正确知识进入 Top-5，并按证据强度决定是否生成回答：

| 用例 | 查询关键词 | 预期知识 ID 前缀 |
| --- | --- | --- |
| KB-010 | 防诈骗和骚扰电话、代理商、被罚多少钱 | `51b17abe` |
| KB-011 | 线上店铺入驻门槛 | `35c01dbd` |
| KB-012 | 大额对外投资并购、法律审核 | `0b5f5cf6` |
| KB-015 | 客户产品需求、响应处理 | `b40b8949` |
| KB-018 | 涉骚扰电话、代理商、处罚金额 | `51b17abe` |
| KB-020 | 实名制、扣分阈值 | `24a0fd9e` |
| KB-021 | 产品问需、初审、评估时限 | `b40b8949` |
| KB-028 | 技能竞赛、团体奖金、2026 修订 | `2b63b216` |

同时，KB-030--034 必须继续全部正确拒答；不得为了提升召回而使 `False Positive Rate` 高于 5%。

### 阶段 4：版本排序、冲突披露与重复候选（KB-009 等）

#### 实现要求

1. 对同一制度/近似标题的多版本候选，引入可解释的版本排序特征，优先级如下：
   - 明确的废止/失效状态；
   - 生效日期；
   - 文号或标题中的年份；
   - 原有检索相关性。
2. 仅在可解析到上述元数据时施加 freshness 加权；无可靠日期时不得凭文件导入时间猜测新旧。
3. 当 Top-K 同时包含冲突版本时，`ask` 应优先用最新有效版本，并披露“本地库同时存在历史版本”的事实；不能静默混用不同版本的金额、标准或适用范围。
4. 对内容 hash 或规范化正文高度相同的重复件，在检索结果层进行聚合/去重，保留一个主记录并以元数据列出等价记录（如可用）；不得物理删除用户数据。

#### 必须新增的测试

- KB-009：2025 差旅费版本应排在 2018/2022 版本之前，回答不得使用禁止事实“区内出差每人每天80元”。
- 多版本并存的 synthetic case：最新有效版本与旧版给出冲突金额时，回答只使用最新版本并给出来源。
- 近似重复的 synthetic case：重复件不应占满 Top-K，也不得改变正确知识的 Top-1 排名。

### 阶段 5：条款型内容的证据完整性（P1-D，KB-019）

#### 实现要求

1. 优先实现“相邻证据扩展”：当命中 block 位于同一知识条目的条、款、项、表格行或连续枚举内容中，向问答上下文补充前后相邻 block，并保留 block ID/顺序溯源。
2. 只有在相邻 block 的文本和顺序可确认时才能拼接；不得跨不同知识条目拼接。
3. 对 `ask` 的数值类回答增加最终事实约束：若回答写入带单位数值，则该数值或其可定位等价表达必须出现在已接受证据/相邻扩展证据中；否则删除该断言或返回证据不足。
4. 审查 `src/services/text_splitter.py` 与实际导入路径。对分号并列的账户类别、表格化规则、编号条款，确保一条完整规则至少能在一个 block 或“主 block + 相邻上下文”中被恢复。
5. 若修改切分算法或索引内容，必须重建测试库索引后复测，并记录前后 block 数；不得用旧索引宣称已修复切分。

#### 必须新增的测试

- 输入包含“II 类 10 万元；III 类 20 万元”的长条款，断言给 III 类问题的可用上下文包含“III 类”和“20 万元”，不把 II 类“10 万元”作为答案。
- KB-019：最终 `ask` 回答必须包含“20万元”、不包含作为答案的“10万元”，并有正确知识 ID `27922ca4` 的可验证引用。
- 无相邻 block 或证据缺失时，不得推测数值；返回 `no_answer` 或明确的证据不足说明。

### 阶段 6：端到端复测与放行判定

1. 使用**原样不改**的 `evals/golden_set_hit_rate.json` 执行 `search`、`read`、`ask` 全流程；服务配置、模型版本、索引时间需记录在报告中。
2. 原始返回仍保存至新目录，例如 `artifacts/hit_rate_test_after_fix/<CaseID>.json`，不得覆盖基线 artifacts。
3. 更新或新建报告，例如 `docs/evaluation/mcp-agent-knowledge-hit-rate-test-report-after-fix.md`。
4. 必须同时报告以下指标，并将引用口径拆分：
   - Top-1 Accuracy；
   - Recall@5；
   - `ask` E2E Pass Rate（检索正确 + 事实正确 + 最终引用有效）；
   - `search` Citation Validity；
   - `ask` Citation Validity；
   - Hallucination Rate；
   - False Positive Rate；
   - 每类查询的分项结果。
5. 单条用例的“总分”不得掩盖 `ask` 失败。若 `ask` 返回空答案、错误事实或无效最终引用，则该条 `E2E Pass=false`，即使 `search` 命中正确文档也不能判定端到端通过。

## 5. 验收标准

### 5.1 必须通过

- 18 个既有 P1 不得保留为同根因失败；KB-019 不得再产生错误数值。
- KB-030--034 的 False Positive Rate 仍为 0%，且不得高于 5%。
- KB-035、KB-037 不得再返回 `requires_current_external_data`。
- KB-017 的 `search`、`ask` 必须都返回正确证据和“2000元/个”结论。
- 实时类查询仍不调用问答生成链路，并返回 `requires_current_external_data`。
- 目标测试文件及相关既有测试全部通过。

### 5.2 指标放行线

| 指标 | 最低通过线 | 推荐目标 |
| --- | ---: | ---: |
| Top-1 Accuracy | >= 75% | >= 85% |
| Recall@5 | >= 88% | >= 95% |
| `ask` E2E Pass Rate | >= 90% | >= 96% |
| ask Citation Validity | >= 95% | >= 98% |
| Hallucination Rate | <= 5% | <= 2% |
| False Positive Rate | <= 5% | <= 5% |

任何资费、处罚、限额、合规、办理规则类的确定性错误答案，均不得放行；即使汇总指标达标，也必须先修复对应 P0/P1。

修复 Agent 应根据实际新增文件调整命令，但至少执行：

```powershell
pytest tests/services/test_relevance_gate_in_corpus.py -v
pytest tests/stability/test_current_information_no_answer.py -v
pytest tests/stability/test_pre_llm_evidence_gate.py -v
pytest tests/mcp/test_hit_rate_regressions.py -v
pytest tests/ -v
```

若阶段 5 修改了分块/索引，先完成测试库重建，再执行 Golden Set 端到端复测。若项目中尚无可重复运行 Golden Set 的脚本，修复 Agent 应补充一个最小的、非破坏性的评估入口；它必须读取既有 Golden Set、支持指定 MCP 端点和 artifacts 输出目录，且不得修改基线数据。

## 7. Agent 执行纪律

1. 先复现，再修改；每项改动说明影响了哪个失败用例。
2. 不得通过修改报告、预期答案或禁用安全 gate 达成“通过”。
3. 不得覆盖 `artifacts/hit_rate_test/` 中的基线证据。
4. 对阈值、正则、排序权重的调整，必须增加针对性单元测试，说明为何不会扩大误答。
5. 若发现报告归因不成立（例如 KB-019 实为重排而非切分），应保留证据、更新归因，并修复真正根因；不得机械执行错误修复。
6. 最终提交中需明确：修改文件、测试命令及结果、复测指标、仍存风险和是否建议生产放行。
