# MCP Agent 知识命中准确率测试方案

> 目的：验证 AI Agent 通过 ShineHeKnowledge MCP 调用知识库时，能否检索到正确知识、给出可验证的回答，并在无依据时避免编造。

## 1. 测试目标与边界

本方案主要评估知识命中质量和证据可靠性，而非模型的语言表达能力。

| 维度 | 验证目标 |
| --- | --- |
| 检索命中 | 正确知识是否被 `search` 召回并排在靠前位置 |
| 原文核验 | Agent 是否能用 `read` 读取并确认命中的原文 |
| 问答可信 | `ask` 的结论是否由检索到的知识和引用支持 |
| 边界处理 | 无答案、歧义、版本冲突时是否避免错误确定性回答 |
| 溯源质量 | 返回的知识 ID、标题、片段或引用是否可定位且支持结论 |

### 不在本轮范围内

- GUI、REST API 性能和并发压测；
- 文档导入、OCR、向量模型训练质量的单独评测；
- Agent 的写作风格、排版或闲聊能力。

## 2. 前置条件

1. 使用已完成索引、内容相对稳定的测试知识库；记录知识库版本、索引完成时间与 `config.yaml` 的检索相关配置。
2. MCP 服务可正常启动，测试 Agent 可以调用 `ping`、`kb_capabilities`、`search`、`read`、`ask`。
3. 测试时固定 MCP 配置档（建议 `extended`）和 Agent 模型版本，避免不同运行环境混入同一轮统计。
4. 测试集的标准答案由熟悉业务的人工提前确认；测试 Agent 不得参与编写标准答案。
5. 对资费、政策、办理规则等高风险内容，标准答案应标注适用地域、渠道、生效时间和版本。

## 3. 标准答案集（Golden Set）设计

建议正式验收使用 70--100 个用例；首次摸底可以先运行 30 个用例。每个用例对应一个已确认的正确知识来源和关键事实。

| 类型 | 建议数量 | 核心验证点 |
| --- | ---: | --- |
| 精确关键词 | 15 | 基础召回、文档标题和正文匹配 |
| 同义词与口语表达 | 15 | 语义检索、业务别称和用户自然表达 |
| 多条件组合 | 10 | 地域、时间、套餐、渠道等条件同时筛选 |
| 跨文档综合 | 10 | 多来源内容的准确整合与分别引用 |
| 易混淆知识 | 10 | 相似产品、不同版本、不同适用对象的区分 |
| 无答案或越界问题 | 10 | 不误命中、不编造、明确说明证据不足 |
| 新旧规则冲突 | 10 | 识别生效时间、版本优先级和废止内容 |

可将用例保存为 JSON 或 JSONL，推荐字段如下：

```json
{
  "case_id": "KB-001",
  "category": "同义词与口语表达",
  "query": "示例：某业务怎么办理？",
  "expected_knowledge_ids": ["knowledge-id-123"],
  "expected_title_keywords": ["某业务", "办理规则"],
  "required_facts": ["条件 A", "条件 B"],
  "forbidden_facts": ["已失效的旧规则"],
  "expected_no_answer": false,
  "notes": "以正文第 3 节为准"
}
```

### 用例编写要求

- 查询应尽量模拟真实 Agent 或一线人员的提问，不只使用文档标题原词。
- 每条可回答用例至少指定一个正确知识 ID 和 1--3 个必须覆盖的关键事实。
- 对多版本内容，必须明确正确版本和错误版本，避免评分人员临时主观判断。
- 无答案用例须确认测试库中确实没有可支撑答案的内容；不要将“答案很难找”误当成“无答案”。

## 4. 测试执行流程

每条用例由测试 Agent 严格按以下步骤执行。

1. 调用 `search(query, top_k=5)`，保存完整返回内容。
2. 记录前五条候选的知识 ID、标题、排名、片段、得分和引用信息。
3. 对排名最高且最可能正确的候选调用 `read(knowledge_id)`，核对正文是否包含标准答案要求的关键事实。
4. 调用 `ask(question)`，要求回答仅依据知识库，并输出对应来源。
5. 根据本方案第 5 节进行评分；对于所有失败或可疑结果，保留原始 MCP 返回，便于复现和定位。

推荐交给测试 Agent 的固定提示词：

```text
你正在执行 ShineHeKnowledge MCP 知识命中准确率测试。

对每个测试用例：
1. 先调用 search，top_k 固定为 5；
2. 选择最相关的候选并调用 read 核验原文；
3. 再调用 ask，检查回答的每项关键结论是否有 MCP 来源支撑；
4. 不得使用自身常识补全、猜测或修正知识库内容；
5. 输出结构化结果：候选排名、引用、关键事实核验、得分、最终判定和问题说明；
6. 对无答案用例，只有在 MCP 结果无法提供充分依据时才能回答“知识库未检索到足够依据”。
```

## 5. 评分规则

### 5.1 可回答用例：每条 10 分

| 指标 | 分值 | 通过标准 |
| --- | ---: | --- |
| Top-1 命中 | 3 | 第一条候选是正确知识条目 |
| Recall@5 命中 | 2 | 正确知识条目进入前五；Top-1 命中时本项同样计分 |
| 关键事实正确 | 2 | 回答或原文覆盖所有 `required_facts`，且无冲突事实 |
| 引用可验证 | 2 | 引用能定位到正确知识，且原文确实支撑结论 |
| 无幻觉或误导 | 1 | 没有无依据扩写、错误合并或使用 `forbidden_facts` |

### 5.2 无答案用例：每条 10 分

| 指标 | 分值 | 通过标准 |
| --- | ---: | --- |
| 未将不相关内容作为答案 | 4 | 没有把相似但不适用的知识判定为答案 |
| 正确表达证据不足 | 3 | 明确说明知识库中没有足够依据，或仅说明已检索到的有限事实 |
| 无编造或虚假引用 | 3 | 不产生无来源结论、不伪造知识 ID 或文档内容 |

### 5.3 核心统计指标

```text
Top-1 Accuracy = Top-1 正确用例数 / 可回答用例总数
Recall@5 = 正确知识进入 Top-5 的用例数 / 可回答用例总数
Answer Groundedness = ask 结论均有充分证据支撑的用例数 / ask 测试总数
Citation Validity = 引用可定位且确实支撑结论的引用数 / 引用总数
Hallucination Rate = 含无依据结论的 ask 用例数 / ask 测试总数
False Positive Rate = 无答案却给出确定性错误答案的用例数 / 无答案用例总数
```

## 6. 验收门槛

| 指标 | 最低通过线 | 推荐目标 |
| --- | ---: | ---: |
| Top-1 Accuracy | >= 75% | >= 85% |
| Recall@5 | >= 88% | >= 95% |
| Answer Groundedness | >= 90% | >= 96% |
| Citation Validity | >= 95% | >= 98% |
| Hallucination Rate | <= 5% | <= 2% |
| False Positive Rate | <= 10% | <= 5% |

对于资费、合规、政策、办理流程等高风险领域，`Citation Validity` 低于 95% 时，本轮不建议作为生产 Agent 的放行依据；若发现任何错误的确定性业务规则，应至少按 P0/P1 缺陷处理。

## 8. 缺陷分级与复测

| 级别 | 定义 | 处理建议 |
| --- | --- | --- |
| P0 | 输出错误的高风险业务规则、资费、政策或合规结论，且表述确定 | 立即停止相关场景放行，修复后全量复测同类用例 |
| P1 | 正确知识存在却未进入 Top-5；或 `ask` 明显曲解原文 | 修复检索/切分/重排/提示词后复测相关类别 |
| P2 | 正确结果存在但排序偏后，或回答遗漏非关键条件、引用不完整 | 纳入迭代，复测受影响用例 |
| P3 | 标题、格式、片段展示等不影响结论正确性的体验问题 | 排期优化 |

每个 P0/P1 缺陷至少应附带以下证据：原始查询、完整 MCP 返回、预期知识 ID、实际错误知识 ID、关键事实对比、运行时间、知识库版本和检索配置。修复后，应运行全部失败用例，并随机抽取同类别不少于 10 条回归用例。

## 9. 最终交付物

测试 Agent 完成后应交付：

1. 标准答案集（JSON/JSONL 或表格）；
2. 每个用例的原始 MCP 调用记录；
3. 按第 7 节模板生成的汇总报告；
4. P0/P1 缺陷清单和可复现证据；
5. 修复建议：明确问题更可能位于文档内容、切分、Embedding、混合检索、重排、元数据还是 `ask` 编排。
